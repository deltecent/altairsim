# SD Systems VDB-8024

**Status:** done

## The real hardware

The **SD Systems VDB-8024** (SD Sales, Dallas TX) is an S-100 **video display board**: an
80-column × 24-line video terminal on one card, with an onboard keyboard interface. It was the
video-console alternative to the SBC-100/200's 8251 serial port — "the video board
and keyboard" instead of a glass teletype. Its raster is generated by an SMC **CRT 5027** video
timer/controller; the terminal logic runs on an **onboard Z80** executing firmware in a PROM,
with a private RAM screen buffer and a programmable **character-generator PROM** (a 2708/2758/
2716). With a monitor and an ASCII keyboard it is a complete terminal.

Configured in period by jumpers only (there is **no host base-address jumper** — the ports are
fixed): CGEN PROM type, cursor style (ships blinking-underline), the two user "special control"
bits, and an optional keyboard→S-100 vectored interrupt. By default the host polls.

## Register reference

Two fixed I/O ports. Both status flags are **active-HIGH**.

| Addr | OUT (write) | IN (read) |
|---|---|---|
| `00` | — (ignored; status is read-only) | **status**: D1 (`0x02`) = a keyboard byte is waiting; D2 (`0x04`) = the display will accept a byte |
| `01` | **display** data — a printable character or a control word (to the terminal engine) | **keyboard** data (7-bit ASCII); reading clears D1 |

## How it is simulated

Despite the "video board" name the VDB-8024 is **not memory-mapped** — the reference is explicit:
to the host it is purely a two-port terminal, and the screen RAM, the CRT-5027 and the onboard Z80
are invisible. So `Vdb8024Board` models the **host-visible terminal**, not the 5027 or the Z80.

- **Decodes** I/O reads/writes on `base` and `base+1` only (default `00`/`01`); no memory, so no
  `peek`/`memMap`.
- **`write(01)`** feeds one byte to a terminal state machine over an internal 80×24 `(char,
  attribute)` grid: printable bytes land at the cursor and advance it; C0 codes and `ESC`
  sequences move/erase/scroll per the v1.6 firmware map.
- **`pump()`** does the host turn: it latches one keyboard byte off a `ByteStream` (the SolBoard
  model — `CONNECT vdb0:keyboard console`) into a holding register, then renders the grid into the
  injected **`Display`** (the VDM-1 model — the two-gate `frameChanged()`/`wantsFrame()` economy,
  glyphs from `sd-vdb8024-font.h`, cursor blink off `Display::hostSeconds()`). It never touches
  SDL; a headless build renders into a `NullDisplay` and a test reads the grid back with
  `screenText()`.
- **Interrupts:** the optional **keyboard-strobe strap** (reference §6: E17→E13-E16). By default
  the host polls status D1. Strapped to a VI line (`interrupt = vi0..vi7`), the board pulls that
  S-100 vectored-interrupt line while a key waits — `assertsVi()` returns the strapped bit, and the
  read of port 01 (the ISR's `IN 01H`) drops it, the implicit end-of-interrupt. The board never
  makes the **vector**: on the real machine the SBC-200's Z80-CTC does, and here the `sbc` board
  does the same (`ch1Triggered()` watches VI2, hands back mode-2 vector `0x02` on IntAck). This is
  what the SD **video CBIOS** needs — the monitor polls, but a booted OS runs the keyboard on the
  interrupt. **DMA:** none.
- **`properties()`:** `port` (the base, fixed at 00 in fact), `cursor` (off/blink/steady), `video`
  (normal/reverse), `interrupt` (the keyboard-strobe VI strap, default `none`). Unit `keyboard`
  carries `connect`.

### Reset

- `Reset::PowerOn` (POC*, cold): blank the page to spaces, home the cursor, clear the attribute,
  drop the keyboard strobe, zero the keystroke counter.
- `Reset::Bus` (RESET*, warm): the onboard Z80 re-runs its power-up path (INIT then CLEAR), so the
  page blanks and the cursor homes; the keyboard strobe drops. (Screen contents do **not** survive
  a reset, because the real terminal's processor reset re-initialized it.)

## Quirks reproduced

| Quirk | If you get it wrong |
|---|---|
| Status is **active-HIGH** (D1 keyboard, D2 display) | `sdmonv21` polls `IN 00 / AND 02` for input and `AND 04` for output; wrong polarity hangs it |
| **Not memory-mapped** — a two-port terminal | Treating it like the VDM-1 (a screen in RAM) invents hardware it never had |
| The **v1.6** control map (CR=`0D`, clear=`1A`, home=`1E`, new-line=`1F`, `ESC =`/`*`/`:`/`T`/`Y`) | The manual's §III "shipped" map reuses `0D` for a speed code — a monitor's CRLF output would corrupt the screen |
| Character-generator **descenders**: a stored byte's bit 0 is a flag, not a dot — a flagged row draws on the two bottom scan lines | `g j p q y , ; ?` render upside-down or with their tail on top |
| `ESC = Y X` takes **row then column**, each `+ 0x20` | Cursor addressing lands transposed |

## Limitations and deliberate departures

- **The onboard Z80, the CRT-5027 and the screen RAM are not emulated** — only their host-visible
  effect. Software that reprogrammed the 5027 registers (onboard ports `80`–`8E`) would find
  nothing there, but no host-side program can: those ports are behind the terminal.
- **Video enhancements** (reverse/blink/half-intensity via `ESC G`/`&`/`'`) are modeled at the
  cell level; **protect** fields are stored but not enforced (this is a display, not a form
  terminal), and `ESC E`/`R` (insert/delete line) are no-ops, exactly as in the v1.6 firmware.
- The **cursor** is drawn as a blinking block, not the hardware's blinking-underline default — a
  cosmetic choice, tunable via `SET vdb0 cursor=…`.

## Verification

`tests/test_vdb8024.cpp`. Unit tests drive the terminal state machine (printable placement,
CR/LF/new-line, wrap, backspace/tab/home/clear, `ESC =` positioning, `ESC T`/`Y` erase, bottom-row
scroll) and the port protocol (D1/D2 polarity, keyboard latch and clear). An acceptance test
builds the `sbc200v` machine by hand, boots the real **`sdmonv21`** ROM, and asserts its `.`
prompt lands on the VDB grid — then types `H 100 200` at the video console and reads the monitor's
answer (`FF00`) back off the screen, proving the keyboard→guest→display loop end to end.
